#Post_184
<b>ساخت یک Software Factory در دل پروژه</b>
#AI_Software_Factory(1/10)

ساخت یک Software Factory می‌تواند از همان Repository فعلی پروژه شروع شود. ورودی این سیستم یک Feature Request است و خروجی آن، تغییری است که مراحل ساخت، Review و Approval را طی کرده و آماده Merge شده است. برای پیاده‌سازی چنین ساختاری می‌توان از Claude Code، مجموعه‌ای از Skills، چند Sub-agent و فایل‌های Markdown استفاده کرد. بخش عمده رفتار سیستم در همین تعریف‌ها و دستورالعمل‌ها قرار می‌گیرد و مقدار کد موردنیاز برای خود Factory می‌تواند کم باشد.

مسیر اجرا با نوشتن Spec آغاز می‌شود، به Builder می‌رسد و سپس وارد Review می‌شود. اگر اصلاح لازم باشد، کار دوباره به Builder برمی‌گردد. در پایان، Approver درباره Merge خودکار یا ارجاع به Human Review تصمیم می‌گیرد. همین مسیر برای Featureهای بعدی دوباره استفاده می‌شود و توسعه را به یک فرایند تکرارپذیر تبدیل می‌کند.

#Post_185
<b>هدایت فرایند با یک Orchestrator Skill</b>
#AI_Software_Factory(2/10)

هماهنگی میان Agentها در یک Software Factory به Orchestrator سپرده می‌شود. این نقش، پایان کار یک Agent را تشخیص می‌دهد و مرحله بعد را آغاز می‌کند؛ برای مثال، پس از آماده‌شدن Spec، اجرای Builder را شروع می‌کند و پس از ساخت Feature، آن را به Reviewerها می‌سپارد. در ساختاری مبتنی بر Claude Code، می‌توان دستورالعمل این هماهنگی را در یک Project Skill تعریف کرد تا برای درخواست‌های بعدی قابل فراخوانی باشد.

اجرای Skill می‌تواند همراه توضیح مستقیم Feature یا درخواست برداشتن کار بعدی از Backlog باشد. عباراتی مانند factory next و factory approve در چنین ساختاری، دستورهایی برای هدایت Agent هستند؛ ادامه عبارت لزوماً یک Schema سخت‌گیرانه ندارد. برای بارگذاری Sub-agentهای تازه‌ساخته‌شده نیز ممکن است Restart کردن Session لازم باشد. فایل Backlog هم کارهای باقی‌مانده را برای اجراهای بعدی نگه می‌دارد.

#Post_186
<b>تکمیل Feature با Reviewهای مستقل</b>
#AI_Software_Factory(3/10)

توسعه یک Feature در Software Factory پس از پایان کدنویسی وارد مرحله Review می‌شود. خروجی Builder می‌تواند هم‌زمان به Agentهای جداگانه برای Security Review، Code Review، UI Review و UX Review سپرده شود. هر Reviewer مسئول بررسی همان حوزه است و نتیجه بررسی خود را به جریان اصلی برمی‌گرداند. این تقسیم نقش اجازه می‌دهد وضعیت بررسی‌های مختلف مستقل دیده شود؛ ممکن است بررسی UI تمام شده باشد، اما Security Review همچنان ادامه داشته باشد.

بازخورد Reviewerها دوباره به Builder داده می‌شود تا اصلاحات را انجام دهد. چرخه ساخت و Review تا رسیدن به نتیجه قابل قبول یا سقف تعیین‌شده ادامه پیدا می‌کند؛ برای نمونه، می‌توان حداکثر دو دور برای آن در نظر گرفت. پس از تکمیل این مرحله، خروجی به Approver می‌رسد تا درباره ادامه مسیر و نیاز به دخالت انسان تصمیم بگیرد.

#Post_187
<b>تعریف مرز میان Approval و Human Review</b>
#AI_Software_Factory(4/10)

موفقیت Reviewها به‌تنهایی به معنای Merge خودکار نیست. در Software Factory، یک Approver می‌تواند پس از بررسی نتیجه کار تصمیم بگیرد که Feature مستقیماً وارد main شود یا در وضعیت نیازمند Human Review باقی بماند. قواعد این تصمیم باید با پروژه ارتباط داشته باشند؛ تغییرات مربوط به Billing یا دسترسی به محتوای دوره، نمونه‌هایی از موضوعاتی هستند که می‌توان برای آن‌ها ارجاع به انسان را تعریف کرد.

بررسی اثر تغییرات نیز می‌تواند باعث توقف شود. برای مثال، تغییری که Render Cache وبلاگ را بی‌اعتبار می‌کند ممکن است به Approval انسانی نیاز داشته باشد. در این وضعیت، Dashboard اطلاعات Feature را نمایش می‌دهد و توسعه‌دهنده با شناسه همان کار، Approval را صادر می‌کند. سپس Branch ساخته‌شده Merge می‌شود و Metadata وضعیت جدید را ثبت می‌کند. بنابراین عبور از Review و اجازه Merge دو مرحله جدا هستند.

#Post_188
<b>نگهداری وضعیت اجرا در Markdown</b>
#AI_Software_Factory(5/10)

نگهداری State یک Software Factory را می‌توان با فایل‌های Markdown انجام داد. اطلاعات مربوط به Spec، نتیجه Build، Reviewها و وضعیت هر کار در پوشه Factory قرار می‌گیرد و Dashboard همین Metadata را برای نمایش مراحل می‌خواند. این ساختار، اطلاعات اجرا را به متن‌هایی تبدیل می‌کند که توسعه‌دهنده می‌تواند مستقیماً در Editor باز کند و Agentها یا سیستم‌های دیگر نیز می‌توانند از آن‌ها استفاده کنند.

تصمیم درباره Commit کردن این اطلاعات به Git، بخشی از طراحی پروژه است. نگهداری همه این فایل‌ها در Repository ممکن است جست‌وجوی فایل‌ها را شلوغ کند؛ در مقابل، قرار دادن آن‌ها در gitignore باعث می‌شود با Clone مجدد Repository منتقل نشوند. اگر Metadata خارج از Git نگهداری شود، برای حفظ آن می‌توان فرایند Backup جداگانه در Cloud Storage در نظر گرفت و مدیریت این فرایند را به Agent سپرد.

#Post_189
<b>مشاهده اجرای Agentها با Dashboard</b>
#AI_Software_Factory(6/10)

مشاهده وضعیت Agentها بخشی از کارکرد یک Software Factory است. یک Dashboard می‌تواند نشان دهد هر Feature در مرحله Spec، Build، Review یا Human Review قرار دارد. هنگام اجرای چند Reviewer، نتیجه هر بررسی جداگانه ظاهر می‌شود و توسعه‌دهنده می‌تواند پیشرفت کار را دنبال کند. همچنین امکان ورود به Sub-agent و دیدن فعالیت آن، جزئیات بیشتری از اجرای همان مرحله در اختیار می‌گذارد.

نمایش وضعیت نیازمند انسان، محل توقف کار را مشخص می‌کند. توسعه‌دهنده می‌تواند اطلاعات Feature را باز کند، علت ارجاع را بررسی کند و سپس Approval بدهد. پس از Merge نیز Metadata به‌روزرسانی می‌شود تا Dashboard نتیجه را نمایش دهد. این Observability شامل دسترسی به Logها و اطلاعات Agentها هم می‌شود و اجازه می‌دهد هنگام پیش‌رفتن کارها، وضعیت چند Feature از یک محل قابل مشاهده باشد.

#Post_190
<b>اجرای موازی Featureها با Git worktree</b>
#AI_Software_Factory(7/10)

اجرای چند Feature به‌صورت هم‌زمان، به پشتیبانی مناسب در Software Factory نیاز دارد. با افزودن Git worktree می‌توان چند کار را در محیط‌های جدا پیش برد و برای هرکدام Session مستقلی از Claude Code اجرا کرد. در این حالت، هر Session یک کار را از Backlog برمی‌دارد و مسیر Spec، Build و Review را دنبال می‌کند. برای مشاهده هم‌زمان Sessionها نیز می‌توان آن‌ها را در بخش‌های جداگانه tmux باز نگه داشت.

نمونه کارهای قابل اجرا در چنین ساختاری، افزودن زمان مطالعه به مقاله، ساخت دکمه Copy برای Code Block و ایجاد صفحه 404 است. Dashboard وضعیت این کارها را هم‌زمان نمایش می‌دهد و هر Feature با سرعت مراحل خودش جلو می‌رود. پس از اضافه‌شدن پشتیبانی Worktree، مدیریت محیط‌های کاری می‌تواند توسط Factory انجام شود و توسعه‌دهنده مجبور نیست مرتب میان آن‌ها جابه‌جا شود.

#Post_191
<b>رفع توقف‌های ناشی از وضعیت Git</b>
#AI_Software_Factory(8/10)

شروع یا Merge یک کار در Software Factory می‌تواند به وضعیت Working Tree وابسته باشد. اگر شرط آغاز کار، Clean بودن Working Tree باشد، تغییرات Commit‌نشده مانع اجرای Feature می‌شوند. در این حالت، ابتدا باید تغییرات موجود تعیین تکلیف و Commit شوند تا Factory بتواند کار جدید را شروع کند. در مرحله Merge نیز شرط Clean بودن Checkout اصلی می‌تواند باعث توقف کاری شود که Reviewهایش را گذرانده است.

تغییرات Backlog نمونه مهمی از این وضعیت هستند، چون هنگام استفاده از خود Factory ایجاد می‌شوند. اگر این تغییرات همیشه Merge را مسدود کنند، قواعد اجرا نیازمند اصلاح‌اند؛ می‌توان برای همان فایل مشخص استثنا تعریف کرد. همچنین تغییرات تازه در کد Factory ممکن است Merge یک Feature دیگر را متوقف کنند. در چنین موقعیتی، ثبت جداگانه تغییرات Factory و سپس ادامه Merge، مسیر تکمیل کار را باز می‌کند.

#Post_192
<b>انتخاب Model با توجه به نقش Agent</b>
#AI_Software_Factory(9/10)

انتخاب Model در یک Software Factory می‌تواند برای نقش‌های مختلف متفاوت باشد. می‌توان نوشتن Spec و Approval را به Opus سپرد و برای برخی Agentهای دیگر از Sonnet استفاده کرد. انتخاب Model مربوط به Orchestrator نیز مستقل از Modelهای Sub-agentهاست؛ تغییر Session اصلی به Sonnet به معنای تغییر خودکار همه Agentهای زیرمجموعه نیست. تنظیم Effort هم در کنار Model، بخشی از پیکربندی اجرای کار است.

سرعت Orchestrator به‌تنهایی زمان پایان Feature را تعیین نمی‌کند، چون پیشرفت کار به سرعت Sub-agentهای مرحله جاری نیز وابسته است. از سوی دیگر، استفاده از Sub-agentها می‌تواند مصرف Token را افزایش دهد، زیرا Context میان Agentها جابه‌جا می‌شود. ارزیابی چنین ساختاری باید هزینه مصرف را در کنار کیفیت خروجی و Observability قرار دهد. اجرای آن نیز می‌تواند در چارچوب Subscription انجام شود و الزاماً به پرداخت مستقیم API متکی نیست.

#Post_193
<b>گسترش Factory از درخواست تا پایش Production</b>
#AI_Software_Factory(10/10)

ورودی یک Software Factory می‌تواند از درخواست مستقیم توسعه‌دهنده فراتر برود. اتصال GitHub Issues اجازه می‌دهد درخواست‌ها از افراد مختلف دریافت شوند و در همان GitHub قابل پیگیری بمانند. همچنین می‌توان Slack را به‌عنوان منبع Trigger در نظر گرفت. در این ساختار، آغاز کار لزوماً به بازکردن دستی یک Session و نوشتن Feature محدود نمی‌ماند و منابع بیرونی می‌توانند کار را وارد مسیر پردازش کنند.

اتصال به Sentry مسیر دیگری برای گسترش Factory است. اطلاعات Bugهای Production می‌تواند همراه Context مرتبط وارد فرایند توسعه شود. همچنین با افزودن Monitoring و Metrics مربوط به CPU و Memory، می‌توان پایش را پس از Deployment ادامه داد. در چنین گسترشی، اگر Feature منتشرشده به نرم‌افزار آسیب بزند، بازگرداندن تغییرات نیز می‌تواند بخشی از همان فرایند باشد. این قابلیت‌ها، مسیر توسعه Factory پس از ساخت چرخه اولیه هستند.
