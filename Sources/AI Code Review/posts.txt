#Post_210  
<b>تعیین عمق Review با Blast Radius</b>
#AI_Code_Review(3/10)

برای انتخاب نقطه شروع Code Review، تصور کن Codebase یک درخت است. Entry Pointها، زیرساخت مشترک و کدی که بخش‌های زیادی به آن وابسته‌اند در تنه قرار می‌گیرند. اگر Agent منطق مشترک Image Rendering را تغییر دهد، اشکال می‌تواند به مسیرهای متعددی برسد که از آن استفاده می‌کنند. همین موضوع درباره تغییر رفتار یک Reducer با Shared State هم صدق می‌کند. در چنین تغییراتی، Diff را دقیق بخوان و اثر تغییر بر مسیرهای وابسته را در نظر بگیر.

در انتهای شاخه‌ها، یک Component مستقل یا منطق تازه‌ای که پشت Feature Gate قرار دارد، Blast Radius محدودتری دارد. برای بررسی چنین تغییری، می‌توانی Diff را سریع مرور کنی و بسته به نوع تغییر، Component Test، Snapshot Test یا Integration Test را ببینی. شناخت Codebase کمک می‌کند سریع تشخیص بدهی کدام تغییر واقعاً مستقل است و کدام تغییر به رفتار مشترک برنامه دست می‌زند.

#Post_211  
<b>بررسی Feature Gate در Code Review</b>
#AI_Code_Review(4/10)

در Code Review یک Feature تازه، نقطه‌ای را پیدا کن که رفتار جدید به مسیر فعلی برنامه وصل می‌شود. اگر Agent یک Component یا منطق جدید را جداگانه ساخته باشد، می‌توان آن بخش را در محدوده خودش بررسی کرد. نقطه اتصال توجه بیشتری می‌خواهد، چون همان‌جا مشخص می‌شود تغییر چه زمانی روی رفتار Production اثر می‌گذارد. طراحی Feature Gate از مرحله برنامه‌ریزی کمک می‌کند این نقطه در Diff قابل تشخیص باشد.

برای یک پیاده‌سازی ساده، Feature Gate می‌تواند یک Boolean Flag باشد که مسیر اجرای کد را تعیین می‌کند. هنگام Review، هر دو وضعیت Flag را در نظر بگیر و ببین با خاموش‌بودن آن، رفتار قبلی برنامه حفظ می‌شود یا نه. اگر بعد از فعال‌سازی مشکلی پیدا شد، باید بتوانی با خاموش‌کردن Gate به همان رفتار برگردی. این امکان روی میزان بررسی لازم برای ادغام تغییر اثر می‌گذارد.

وقتی یک Agent کد را می‌نویسد، گفت‌وگوی پیاده‌سازی روی برداشتش از تغییر اثر می‌گذارد. اگر همان Agent در همان Context نقش Reviewer را بگیرد، ممکن است در بازبینی به فرض‌ها و تصمیم‌های قبلی تکیه کند. برای Adversarial Review، Diff را به یک Agent تازه یا Subagent جداگانه بده که Context تولید کد را نداشته باشد. به این شکل، بازبینی از روی تغییر انجام می‌شود و فرض‌های گفت‌وگوی پیاده‌سازی به Reviewer منتقل نمی‌شوند.

برای اجرای این مرحله می‌توانی از Review داخلی Codex یا Claude Code شروع کنی. اگر برای بازبینی روال مشخصی داری، آن را در Review Skill تعریف کن تا Reviewer بداند چه بررسی‌هایی باید انجام دهد. Agent سازنده همچنان می‌تواند در زمان پیاده‌سازی کدش را اعتبارسنجی و اصلاح کند. بازبینی مستقل وقتی انجام می‌شود که Diff برای بررسی آماده است.

#Post_217  
<b>اعتبارسنجی کد پس از Launch محدود</b>
#AI_Code_Review(10/10)

پس از Code Review و بررسی آمادگی Feature برای Launch، می‌توان رفتار آن را با بخشی از ترافیک واقعی بررسی کرد. در Canary Deployment، Feature Gate کمک می‌کند تغییر ابتدا برای گروه کوچکی فعال شود. بعد از فعال‌سازی، دنبال باگ، Crash یا Alert بگرد تا مشکلاتی را که با ورود ترافیک واقعی ظاهر می‌شوند زودتر ببینی. اگر مشکلی پیدا شد، می‌توانی با خاموش‌کردن Gate، Feature را غیرفعال کنی و به رفتار قبلی برگردی.

در یک گروه کاربری کوچک، A/B Testing ممکن است توان آماری کافی برای مقایسه معتبر دو نسخه را نداشته باشد. با این حال، فعال‌سازی محدود همچنان فرصتی برای مشاهده خطاها و هشدارها فراهم می‌کند. تست‌ها و شواهد PR برای بررسی پیش از Merge به کار می‌آیند و Launch محدود امکان بررسی رفتار کد را در Production فراهم می‌کند.
