<b>مجموعهٔ Refactor کد قدیمی با AI</b>  
#AI_Legacy_Refactor(1/10)

وقتی یک Agent ساختار کد قدیمی را تغییر می‌دهد، از کجا می‌فهمی رفتار برنامه عوض نشده؟ ممکن است یک Job به ترتیب فعلی خروجی وابسته باشد یا گزارشی از متن مشخصی در Log استفاده کند. این وابستگی‌ها همیشه مستند نیستند و گاهی یک تغییر کوچک در ظاهر، نتیجه‌ای را عوض می‌کند که بخش دیگری از سیستم روی آن حساب کرده است.

در این مجموعه، کار را با شناخت یک ماژول و ثبت رفتار فعلی آن با Characterization Test شروع می‌کنیم. بعد می‌بینیم چطور محدودهٔ تغییرات Agent را مشخص کنیم، Refactor را در Commitهای کوچک جلو ببریم و Diff را برای تغییرات ناخواسته بررسی کنیم. برای کارهای بزرگ‌تر هم به مدیریت چند Branch و جایگزینی تدریجی بخش‌های قدیمی می‌رسیم.

#Post_219  
<b>حفظ رفتار فعلی در Refactor</b>  
#AI_Legacy_Refactor(2/10)

وقتی برای اولین بار Refactor کد قدیمی را به Agent می‌سپاری، از یک ماژول شروع کن که زیاد تغییر می‌کند و مرتب دچار مشکل می‌شود. یک Coding Agent می‌تواند زنجیرهٔ فراخوانی‌ها را دنبال کند، تابع‌ها را جابه‌جا کند و تست‌ها را دوباره اجرا کند. بخش دشوار کار، تشخیص قراردادهای مستندنشده است. برای نمونه، ممکن است تغییر مرحلهٔ گرد کردن مبلغ، قاعده‌ای را عوض کند که یکی از مشتریان سال‌هاست به آن متکی است.

پیش از تغییر ساختار، رفتار فعلی ماژول را با تست ثبت کن. اگر حین بررسی به موردی برخوردی که شبیه باگ است، آن را یادداشت کن تا بتوانی حفظ رفتار را در همان Refactor بررسی کنی. بعد از اینکه ماژول تست و ساختار مناسب‌تری داشت، هر باگ ثبت‌شده را در تغییری جداگانه و با تست خودش اصلاح کن.

#Post_220  
<b>شناخت Codebase پیش از اولین تغییر</b>  
#AI_Legacy_Refactor(3/10)

پیش از ویرایش، از Agent بخواه ماژول را در حالت Read-only بررسی کند. بررسی را از Entry Pointها شروع کن و یک جریان واقعی را تا خروجی دنبال کن. در یک ماژول صورتحساب، این جریان می‌تواند از ایجاد فاکتور تا تولید PDF باشد. در طول مسیر، علاوه بر نام تابع‌ها، Side Effectهایی مثل نوشتن در دیتابیس، تماس شبکه و Logهایی را ثبت کن که احتمال دارد ابزار دیگری آن‌ها را بخواند. وابستگی به Global State، متغیرهای محیطی، زمان و Locale هم بخشی از همین بررسی است.

برای بخش‌های بزرگ‌تر می‌توان بررسی یک مسیر مشخص را به Subagent سپرد و نتیجه را در Repo نگه داشت. اگر Agent کدی را بلااستفاده تشخیص داد، قبل از حذف با جست‌وجو و Runtime Log بررسی کن. ممکن است آن کد از طریق Reflection، تنظیمات یا یک Cron Job بیرون از Repo فراخوانی شود.

#Post_221  
<b>ثبت رفتار کد با Characterization Test</b>  
#AI_Legacy_Refactor(4/10)

برای ساخت Characterization Test، از Agent بخواه کد فعلی را با ورودی‌های مختلف اجرا کند و خروجی مشاهده‌شده را مبنای Assertion قرار دهد. برای محاسبهٔ فاکتور، ورودی‌هایی مثل تعداد صفر یا منفی، تخفیف بالای صد درصد و مبالغی که نیاز به گرد کردن دارند، رفتارهای مرزی را نشان می‌دهند. اگر خروجی شبیه باگ بود، همان خروجی را ثبت کن و مورد مشکوک را یادداشت کن. برای خروجی پیچیده، می‌توان ورودی و نتیجه را در فایل ذخیره کرد و هر بار با یک Golden Master مقایسه کرد.

پیش از Refactor، مطمئن شو تست‌ها روی کد دست‌نخورده پاس می‌شوند. بعد با تغییری عمدی و موقت، مثل عوض کردن ترتیب مرتب‌سازی، بررسی کن که دست‌کم یکی از تست‌ها شکست بخورد. اگر تست فقط نبود Exception را بررسی می‌کند یا تابع اصلی را Mock کرده، Assertion را طوری اصلاح کن که رفتار واقعی را بسنجد.

#Post_223  
<b>اجرای Refactor در Commitهای کوچک</b>  
#AI_Legacy_Refactor(6/10)

برای Refactor یک ماژول بزرگ، ابتدا در Plan Mode هدف را به چند تغییر کوچک و مشخص تبدیل کن. مثلاً اگر `BillingService` محاسبهٔ مالیات، منطق فاکتور و تولید PDF را یک‌جا انجام می‌دهد، استخراج منطق مالیات می‌تواند قدم اول باشد. طرح را تا جایی بازبینی کن که هر قدم یک Refactor مشخص داشته باشد و بتوان آن را در یک Commit با نام روشن ثبت کرد.

بعد از اجرای هر قدم، نتیجهٔ تست‌ها و Diff را با طرح همان قدم مقایسه کن. در استخراج منطق مالیات، انتظار داری بیشتر تغییرات مربوط به جابه‌جایی کد و به‌روزرسانی Importها باشد. اگر تست‌ها پاس شدند و Diff با محدودهٔ تعیین‌شده همخوانی داشت، همان قدم را Commit کن و به مرحلهٔ بعد برو. با این ترتیب، وقتی تستی شکست می‌خورد، راحت‌تر می‌توان تغییر مسئول را پیدا کرد.

#Post_224  
<b>تنظیم اندازهٔ Refactor بر اساس ریسک</b>  
#AI_Legacy_Refactor(7/10)

برای تعیین اندازهٔ یک قدم Refactor، ببین آن تغییر چه نوع ریسکی دارد. در Rename یا جابه‌جایی تابع، دنبال ارجاع‌هایی بگرد که در String، Config یا Reflection پنهان شده‌اند. هنگام تقسیم یک کلاس یا ماژول بزرگ، Circular Import و تغییر ترتیب Initialization را بررسی کن. اگر قرار است Library یا API عوض شود، تفاوت در مقدارهای پیش‌فرض، نوع خطا و نحوهٔ پردازش Time Zone اهمیت پیدا می‌کند.

تغییر در Concurrency یا Async Model به قدم‌های کوچک‌تر و تست‌های هدفمند نیاز دارد، چون Race Conditionها به‌راحتی در تست دیده نمی‌شوند. در تغییر Data Model یا Schema هم داده‌های موجود، Migration و سرویس‌هایی را در نظر بگیر که همان جدول را می‌خوانند. برای تغییرهای مکانیکی و تکراری، می‌توان از یک Codemod استفاده کرد تا تبدیل یکسانی روی فایل‌ها اعمال شود.

#Post_225  
<b>کشف تغییرات ناخواسته در Diff</b>  
#AI_Legacy_Refactor(8/10)

هنگام Code Review یک Refactor، مسیرهایی را بخوان که تغییر رفتارشان ممکن است از پوشش تست‌ها بیرون مانده باشد. عوض شدن نوع Exception یا حذف یک Sort می‌تواند نتیجهٔ کد را تغییر دهد. جایگزینی بررسی صریح `None` با Truthiness Check هم ممکن است رفتار ورودی‌هایی مثل `0` و رشتهٔ خالی را عوض کند. در Diff به زمان گرد کردن اعداد، تبدیل UTC به زمان محلی و تغییر متن Log هم توجه کن، چون ممکن است کد دیگری به همان رفتار وابسته باشد.

برای بررسی دوباره، Diff را به Agent دیگری در یک Session تازه بده و خودت هم تغییرات را مرور کن. فایل‌هایی را که خارج از محدودهٔ قدم فعلی تغییر کرده‌اند پیدا کن. اگر Characterization Test شکست خورد، مقدار مورد انتظار را نگه دار و تصمیم بگیر که تغییر را Revert کنی یا تغییر رفتار را آگاهانه بپذیری.

#Post_226  
<b>مدیریت Refactor چندروزه با Git Worktree</b>  
#AI_Legacy_Refactor(9/10)

وقتی Refactor چند روز طول می‌کشد، کار را به تسک‌های مستقل تقسیم کن و برای هر قدم یا ماژول یک Branch جدا در نظر بگیر. با Git Worktree، چند Session از Agent می‌توانند روی Branchهای متفاوت همان Repo کار کنند. وقتی بررسی‌های یک تغییر پاس شد، PR کوچک آن را Merge کن تا Branchها برای مدت طولانی از `main` فاصله نگیرند. اگر تغییری مسیر اجرا را عوض می‌کند، Feature Flag امکان برگشت بدون Deploy دوباره را فراهم می‌کند.

طرح را در Repo نگه دار و وضعیت هر تسک را بعد از انجام ثبت کن. اگر یک Session قطع شد، Session بعدی می‌تواند از اولین مورد انجام‌نشده ادامه دهد. در Claude Code، فرمان `claude --continue` هم می‌تواند آخرین Session همان دایرکتوری را بازیابی کند تا Context مرحلهٔ شناخت Codebase در دسترس بماند.
