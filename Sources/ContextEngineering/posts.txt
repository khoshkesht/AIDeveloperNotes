#Context_Engineering(1/18)
<b>وقتی Context به مسئله تبدیل می‌شود</b>

گاهی Agent در ابتدای کار پاسخ‌های مناسبی می‌دهد، اما با ادامه تعامل، نتیجه به‌تدریج ضعیف‌تر می‌شود. این تغییر لزوماً به این معنا نیست که Model ضعیف شده یا باید Model یا Harness را عوض کرد. یکی از علت‌های اصلی می‌تواند پر شدن Context و انباشته شدن اطلاعات در آن باشد.

فضایی که Model در اختیار دارد محدود است و همه‌چیز، از instructions و محتوای موردنیاز گرفته تا code، chat history و اطلاعات دیگر، باید در همین فضا قرار بگیرد. هرچه اطلاعات بیشتری در این فضای محدود جمع شود، هم کیفیت پاسخ می‌تواند کاهش پیدا کند و هم هزینه افزایش می‌یابد، چون Tokenهای بیشتری پردازش می‌شوند. مدیریت این فضای محدود، یکی از مسائل اصلی Context Engineering است.

#Post_152
#Context_Engineering(2/18)
<b>دو مسئله متفاوت در مدیریت Context</b>

مدل‌ها به‌صورت ذاتی stateless هستند. اگر یک کاربر session جدیدی باز کند و چیزی پیرامون Model ساخته نشده باشد، Model از اتفاقات session قبلی اطلاعی ندارد و عملاً از صفر شروع می‌کند. در مقابل، داخل یک session نیز مسئله دیگری وجود دارد: Context به‌مرور با اطلاعات مختلف پر می‌شود و باید مشخص شود چه چیزی در آن باقی بماند.

اینجا دو مسئله جدا شکل می‌گیرد. Context Management به مدیریت اطلاعات داخل یک session مربوط است، در حالی که Memory اطلاعات موردنیاز در چند session را پوشش می‌دهد. پیش از طراحی Memory پیچیده، باید بتوان یک session را به‌درستی مدیریت کرد. Context Engineering در این سطح یعنی تصمیم‌گیری درباره اینکه Model در هر فراخوانی چه چیزی ببیند، چه چیزی حذف شود و چه زمانی Context تغییر کند.

#Post_153
#Context_Engineering(3/18)
<b>آنچه واقعاً Context را پر می‌کند</b>

وقتی با یک Agent کار می‌کنیم، Context فقط شامل سؤال فعلی کاربر نیست. system prompt، تعریف Toolها و نحوه استفاده از آن‌ها، chat history، خروجی Toolهای قبلی، اطلاعات بازیابی‌شده و خود درخواست کاربر همگی می‌توانند هم‌زمان وارد Context شوند. حتی درخواست کاربر ممکن است شامل حجم زیادی code یا error log باشد.

بخش قابل‌توجهی از رشد Context می‌تواند از old tool outputs ایجاد شود؛ مانند chunkهای بازیابی‌شده، جفت‌های tool call و tool result، fileها و searchهای قبلی. باقی ماندن همه این اطلاعات فقط هزینه را افزایش نمی‌دهد؛ Context بزرگ‌تر می‌تواند کیفیت را نیز کاهش دهد و با افزایش TTFT، زمان رسیدن اولین Token را بیشتر کند. بنابراین کوچک نگه داشتن Context هم مسئله کیفیت است، هم هزینه و هم latency.

#Post_154
#Context_Engineering(4/18)
<b>کوچک‌ترین Context کافی با Compaction</b>

هدف Compaction نگه داشتن کوچک‌ترین Context ممکن است که هنوز اطلاعات کافی برای پاسخ دادن را داشته باشد. اطلاعات غیرضروری می‌توانند حذف شوند یا جایی دیگر ذخیره شوند تا در صورت نیاز دوباره در دسترس قرار بگیرند. برای شروع هم الزاماً نیازی به استفاده از یک Model بزرگ نیست.

روش‌های ساده‌ای مثل truncate کردن خروجی‌های غیرعادی Toolها یا استفاده از sliding window می‌توانند مؤثر باشند. اگر یک Tool به‌جای چند خط، صدها خط خروجی تولید کند، می‌توان فقط ابتدا و انتهای آن را نگه داشت و مشخص کرد که خروجی truncate شده است. در sliding window نیز فقط تعداد مشخصی از turnهای اخیر حفظ می‌شوند. برای بعضی Toolها حتی می‌توان بخش عمده خروجی‌های قدیمی را همیشه پاک کرد.

#Post_155
#Context_Engineering(5/18)
<b>انتخاب هوشمند اطلاعات با Selective Retention</b>

گاهی قواعد ساده برای حذف Context کافی نیستند و می‌توان از Model برای تصمیم‌گیری درباره اطلاعات باقی‌مانده استفاده کرد. در Selective Retention، Model با توجه به مسیری که گفتگو طی می‌کند تشخیص می‌دهد چه اطلاعاتی باید حفظ و چه اطلاعاتی حذف شوند. در آزمایش‌های انجام‌شده، این روش یکی از تکنیک‌هایی بود که تأثیر بیشتری در Compaction داشت.

برای این کار الزاماً به Modelهای بزرگ نیاز نیست و حتی Modelهای کوچک یا local نیز می‌توانند برای برخی تکنیک‌های Compaction استفاده شوند. ایده اصلی این است که مقداری Token برای تصمیم‌گیری درباره Context مصرف شود تا در ادامه Tokenهای بیشتری ذخیره شوند. در نتیجه Compaction فقط کوتاه کردن مکانیکی history نیست؛ می‌تواند فرآیندی باشد که درباره ارزش اطلاعات موجود در Context تصمیم می‌گیرد.

#Post_156
#Context_Engineering(6/18)
<b>خلاصه‌سازی و Delta Summarization</b>

یکی از ساده‌ترین روش‌های Compaction، summarization است. بخشی از turnهای قبلی به‌صورت مداوم خلاصه می‌شوند یا وقتی Context به یک حد مشخص رسید، کل history به یک summary تبدیل می‌شود و session با همان summary ادامه پیدا می‌کند. این روش اجازه می‌دهد به‌جای نگهداری تمام جزئیات قبلی، نسخه فشرده‌تری از گفتگو در Context باقی بماند.

روش دیگری به نام delta summarization برای کار با sub-agentها مطرح می‌شود. در این روش یک summary نگهداری می‌شود و با ایجاد summaryهای جدید، همان نسخه قبلی به‌مرور به‌روزرسانی می‌شود؛ سپس sub-agent نتیجه فشرده‌شده را به Agent اصلی تحویل می‌دهد. با این حال اضافه کردن sub-agent همیشه ضروری نیست؛ اگر یک Agent اصلی به‌تنهایی عملکرد مناسبی داشته باشد، افزودن این پیچیدگی توجیهی ندارد.

#Post_157
#Context_Engineering(7/18)
<b>خارج کردن اطلاعات از Context</b>

راه دیگر برای کنترل Context این است که همه اطلاعات را دائماً داخل آن نگه نداریم. بخشی از اطلاعات می‌تواند در Memory، documentation یا ساختاری مبتنی بر RAG ذخیره شود و فقط هنگام نیاز دوباره وارد Context شود. این رویکرد اطلاعات را از بین نمی‌برد و امکان مراجعه دوباره به آن‌ها را حفظ می‌کند.

یک ساختار قابل استفاده این است که اطلاعات به chunkها تقسیم شوند، chunkها با pointer به یکدیگر و به raw data متصل باشند و یک index کوچک مسیر دسترسی به آن‌ها را نگه دارد. Agent ابتدا فقط index را می‌بیند؛ سپس در صورت نیاز chunk مرتبط و در مرحله بعد raw data را می‌خواند. در نتیجه مقدار Context متناسب با پیچیدگی Task افزایش پیدا می‌کند: Task ساده اطلاعات کمتر و Task پیچیده اطلاعات بیشتری دریافت می‌کند.

#Post_158
#Context_Engineering(8/18)
<b>بارگذاری تدریجی با Progressive Disclosure</b>

یکی از الگوهای مدیریت Context استفاده از Skillهای کوچک‌تر و دقیق‌تر است. به‌جای قرار دادن حجم زیادی از اطلاعات در یک Skill، می‌توان Skillهای کوچک ساخت که در صورت نیاز به یکدیگر ارجاع دهند. در این حالت لازم نیست همه اطلاعات از ابتدا در Context قرار بگیرند و Skillها می‌توانند یکی‌یکی بارگذاری شوند.

همین الگو امکان ایجاد sub-agent با Context اختصاصی یک Skill را نیز فراهم می‌کند. مفهوم اصلی Progressive Disclosure همین است: فقط چیزی را Load کن که در همان لحظه موردنیاز است. این روش Context را با نیاز واقعی Task هماهنگ می‌کند و از وارد کردن پیشاپیش اطلاعاتی که ممکن است هرگز استفاده نشوند جلوگیری می‌کند. در ساختارهای مبتنی بر index و chunk نیز همین منطق دیده می‌شود؛ ابتدا نمای کوچک و سپس جزئیات موردنیاز بازیابی می‌شوند.

#Post_159
#Context_Engineering(9/18)
<b>تعارض Compaction با Prompt Caching</b>

در یک گفتگوی چندمرحله‌ای، سؤال جدید معمولاً همراه Tokenهای قبلی دوباره پردازش می‌شود. Prompt Caching اجازه می‌دهد بخشی از محاسبات مربوط به Tokenهای قبلی ذخیره و دوباره استفاده شود. Tokenهای cached می‌توانند بسیار ارزان‌تر باشند و چون قبلاً محاسبه شده‌اند، زمان رسیدن به پاسخ اولیه را نیز کاهش دهند.

اما Compaction می‌تواند همین مزیت را از بین ببرد. وقتی Context خلاصه یا transform می‌شود، Context جدید دیگر با نسخه cached یکسان نیست و ممکن است Cache قابل استفاده نباشد. در آزمایش‌های مطرح‌شده، این موضوع باعث شد summarization همیشه گزینه اقتصادی‌تری نباشد. بنابراین هدف نباید خلاصه کردن دائمی Context باشد؛ باید بین کاهش Context و حفظ cache hit تعادل برقرار شود و Compaction فقط در شرایط مناسب انجام گیرد.

#Post_160
#Context_Engineering(10/18)
<b>مهندسی Context بدون Observability ناقص است</b>

انتخاب تکنیک مناسب Context Management بدون اندازه‌گیری قابل اتکا نیست. برای هر turn می‌توان input tokens، output tokens، تعداد cached tokens، cost، TTFT، تعداد tool callها و وقوع summarization را ثبت کرد. این داده‌ها امکان مقایسه واقعی رفتار تکنیک‌های مختلف را فراهم می‌کنند، نه قضاوت بر اساس اینکه یک روش در ظاهر هوشمندانه به نظر می‌رسد.

ثبت رفتارهای غیرعادی نیز بخشی از همین فرایند است. cache hit rate، خروجی‌های غیرعادی طولانی، رفتارهای عجیب و حتی نشانه‌های نارضایتی کاربر می‌توانند Log شوند. دلیل این سطح از Observability ساده است: بعضی تکنیک‌هایی که از نظر معماری جذاب به نظر می‌رسند، در عمل ممکن است سودی نداشته باشند یا حتی نتیجه را بدتر کنند. Context Engineering بدون Eval و داده واقعی، به مجموعه‌ای از فرضیات تبدیل می‌شود.

<b>دو مسیر برای Retrieval</b>

وقتی Knowledge Base از Context Window بزرگ‌تر باشد، باید فقط اطلاعات مرتبط بازیابی شوند. یک روش، Hybrid Search است که semantic search را با keyword search ترکیب می‌کند. در پیاده‌سازی بررسی‌شده، ابتدا نتایج semantic similarity و BM25 گرفته می‌شوند، سپس نتایج ترکیب و rerank می‌شوند تا مرتبط‌ترین chunkها به Agent برسند.

مسیر دیگر این است که Agent خودش Knowledge Base را مانند file system مرور کند. برای این کار ساختاری شامل raw files، فایل‌های generated و wiki ساخته شد و Agent با Bash commandهای read-only در آن جستجو می‌کرد. Sandbox دسترسی را به همان پوشه محدود می‌کرد و برای زمان اجرای command، اندازه tool output و تعداد commandها نیز محدودیت وجود داشت. این روش امکان exploration مستقیم Knowledge Base را به Agent می‌داد.

#Post_163
#Context_Engineering(13/18)
<b>ارزیابی Context باید چندمرحله‌ای باشد</b>

ارزیابی Context Management فقط با چند سؤال کوتاه کافی نیست. برای single-turn از سؤال‌وجواب‌های واقعی کاربران استفاده شد و داده‌های قدیمی یا تکراری کنار گذاشته شدند. سپس بررسی شد آیا سیستم lesson صحیح را retrieve کرده و آیا پاسخ شامل facts موردانتظار بوده است. بخشی از grading مستقیماً با code و بخشی با LLM as a Judge انجام شد.

برای multi-turn، یک fact در ابتدای گفتگو قرار می‌گرفت، سپس تعداد زیادی پیام filler اضافه می‌شد و در ادامه یک probe بررسی می‌کرد که Model هنوز آن fact را به یاد دارد یا نه. علاوه بر کیفیت پاسخ، خود اجرای تکنیک نیز کنترل می‌شد تا مثلاً مشخص شود Compaction واقعاً trigger شده است. latency، TTFT و سایر metricها نیز در report نهایی ثبت می‌شدند.

<b>وقتی Full History از Compaction بهتر عمل می‌کند</b>

در مقایسه چندین روش Context Management، یک نتیجه غیرمنتظره به دست آمد: نگه داشتن Full History بهترین روش برای بازیابی اطلاعات در گفتگوهای چندمرحله‌ای بود. تنظیمات production که برای پاک کردن خروجی‌ها و summarization طراحی شده بودند، عملکرد پایین‌تری داشتند و در آزمایش multi-turn کیفیت آن‌ها تا ۳۸ درصد کاهش پیدا کرد.

#Post_165
#Context_Engineering(15/18)
<b>هزینه کمتر با Token بیشتر</b>

تعداد Token بیشتر الزاماً به معنای هزینه بیشتر نیست. در آزمایش DeepSeek، Full History بیشترین Token را ارسال می‌کرد، اما ارزان‌ترین روش بود. دلیل این رفتار Prompt Caching بود؛ حدود ۹۷ درصد Tokenهای ارسال‌شده cached بودند و Tokenهای cached هزینه بسیار کمتری نسبت به Tokenهای جدید داشتند.

این نتیجه حتی در یک conversation با ۳۶ turn و حدود ۱.۷۸ میلیون Token نیز حفظ شد. در مقابل، summarization در هر turn باعث تولید و پردازش Tokenهای جدید می‌شد و مزیت Cache را کاهش می‌داد. همچنین در آزمایش memory، Full History توانست جزئیات موردنظر را در ۹۵ درصد موارد برگرداند، در حالی که summarization یا Compaction این عدد را به ۳۲ درصد رساند؛ زیرا بخشی از جزئیات لازم هنگام خلاصه‌سازی از دست می‌رفت.

#Post_166
#Context_Engineering(16/18)
<b>زمینه طولانی همیشه دچار Context Rot نمی‌شود</b>

بزرگ شدن Context الزاماً به این معنا نیست که Model دیگر نمی‌تواند جزئیات قبلی را پیدا کند. در آزمایش Long Context، برای facts مشخص و متمایز، Model حتی تا حدود ۸۰۰ هزار Token نیز نتایج خوب و پایداری ارائه کرد و آن facts را از دست نداد. برای facts مبهم‌تر عملکرد پایین‌تر بود و تقریباً به نصف حالت facts متمایز رسید.

این رفتار با نتایج memory نیز هم‌جهت بود: نگه داشتن کل chat حدود ۹۵ درصد جزئیات را بازیابی کرد، در حالی که summarization حدود ۳۲ درصد نتیجه داشت. بنابراین Compaction نباید صرفاً به دلیل طولانی شدن Context به‌صورت پیش‌فرض فعال شود. نتیجه عملی آزمایش‌ها این بود که ابتدا باید constraint مشخص شود و سپس بر اساس همان محدودیت، راه‌حل مناسب انتخاب شود.

<b>وقتی Retrieval از Context بزرگ بهتر است</b>

شرایط برای local Model متفاوت است. در آزمایش انجام‌شده روی MacBook، Context Window به 32K محدود بود و بعضی lessonها به‌تنهایی از این مقدار بزرگ‌تر بودند. وقتی conversation دیگر در Context Window جا نمی‌گرفت، Caching هم مسئله را حل نمی‌کرد و Context باید با compression یا Retrieval کوچک‌تر می‌شد. افزایش اندازه Model نیز محدودیت Context Window را برطرف نمی‌کرد.

برای documentهای بزرگ، Retrieval نتیجه بسیار بهتری داشت و در آزمایش مربوطه به ۱۰۰ درصد accuracy رسید. همچنین semantic search به‌تنهایی در مقیاس بزرگ پایدار نبود: Dense RAG در محدوده 50K تا 200K حدود ۸۰ درصد عملکرد داشت، اما در 400K برای facts مدفون به صفر recall رسید؛ در همان آزمایش BM25 همچنان ۱۰۰ درصد نتیجه داشت. به همین دلیل ترکیب Dense Retrieval و BM25 در Hybrid Search استفاده شد.

<b>فشرده‌سازی را به انتخاب پیش‌فرض تبدیل نکنید</b>

نتیجه نهایی آزمایش‌ها یک قاعده ساده داشت: Compaction نباید رفتار پیش‌فرض سیستم باشد. ابتدا باید constraint واقعی مشخص شود. اگر Context در window جا می‌شود و Prompt Caching مؤثر است، نگه داشتن Full History می‌تواند از نظر recall، latency و حتی cost بهتر باشد. اگر محدودیت سخت Context Window وجود دارد، آن‌وقت compression یا Retrieval معنا پیدا می‌کند.

در تنظیم نهایی سیستم، DeepSeek V4 Flash به دلیل هزینه و محدودیت‌های سخت‌افزاری انتخاب شد، Hybrid Retrieval برای دسترسی به اطلاعات باقی ماند و history تا حد ممکن کامل نگهداری شد. Compaction نیز به‌جای اجرای مداوم، بعد از رسیدن Context به حد 30K Token در نظر گرفته شد. این تصمیم حاصل مقایسه عملی روش‌ها بود: Context Engineering یعنی انتخاب آنچه Model باید ببیند بر اساس constraint و Eval، نه کوچک کردن Context به هر قیمت.
