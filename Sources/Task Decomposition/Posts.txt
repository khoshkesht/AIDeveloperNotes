<b>زنجیره‌سازی برای اجرای مرحله‌ای</b> 
 
یکی از ساده‌ترین شکل‌های Task Decomposition، استفاده از Prompt Chaining است. در این الگو، خروجی یک Prompt مستقیماً به ورودی Prompt بعدی تبدیل می‌شود. به‌جای اینکه یک Agent همه تحلیل را در یک مرحله انجام دهد، workflow می‌تواند ابتدا داده را استخراج کند، سپس نتیجه را تحلیل کند و در نهایت از خروجی تحلیل برای تولید پاسخ نهایی استفاده کند. این ساختار برای کارهایی مناسب است که مراحل آن وابستگی طبیعی و مشخصی دارند. [Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/aaai-apply-task-decomposition-multi-agent-azure/2-design-prompt-chain-workflows)

نکته مهم این است که هر مرحله باید یک وظیفه مشخص داشته باشد. اگر مرحله دوم بدون خروجی مرحله اول قابل اجرا نیست، یک Linear Chain طبیعی شکل می‌گیرد. در مقابل، اگر نتیجه یک مرحله تعیین کند مرحله بعدی کدام مسیر باشد، workflow می‌تواند به Branching Chain تبدیل شود و مسیر اجرای بعدی را در runtime انتخاب کند. <b>انتخاب میان Static و Dynamic Decomposition</b> 
 
در Static Decomposition، ساختار Taskها هنگام طراحی سیستم مشخص می‌شود. این رویکرد برای درخواست‌هایی مناسب است که الگوی ثابت و قابل پیش‌بینی دارند؛ توسعه‌دهنده از قبل می‌داند چه مراحلی باید اجرا شوند و ترتیب آن‌ها چیست. مزیت اصلی آن predictability و Debug ساده‌تر است، اما نمی‌تواند خود را با تفاوت زیاد میان درخواست‌ها تطبیق دهد. [Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/aaai-apply-task-decomposition-multi-agent-azure/3-implement-dynamic-adaptive-task-decomposition)

در Dynamic Decomposition، یک LLM ابتدا خود درخواست را تحلیل می‌کند و در runtime تصمیم می‌گیرد چه Taskهایی لازم‌اند. یک درخواست ساده ممکن است فقط یک عملیات نیاز داشته باشد، در حالی که درخواست پیچیده به چند مرحله تحلیل نیاز دارد. این انعطاف هزینه دارد: Meta-Agent اولیه باعث افزایش Token، Latency و Coordination می‌شود. بنابراین Dynamic Decomposition زمانی ارزش دارد که پیچیدگی و ساختار درخواست‌ها واقعاً متغیر باشد. [Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/aaai-apply-task-decomposition-multi-agent-azure/3-implement-dynamic-adaptive-task-decomposition)

بهترین سطح Decomposition را نمی‌توان فقط از روی معماری حدس زد. می‌توان یک workload مشابه را با Single Agent، تعداد متوسط Agent و ساختار ریزتر اجرا کرد و Latency، Token Consumption و Quality را مقایسه کرد. افزایش تعداد Agentها ممکن است ابتدا جهش محسوسی در کیفیت ایجاد کند اما پس از نقطه‌ای، هزینه Coordination سریع‌تر از Quality رشد کند. Agent دریافت‌کننده نیز باید بتواند بر اساس capability خودش Task را قبول یا رد کند. اگر Task خارج از domain آن باشد، انتقال باید به Agent مناسب دیگری انجام شود، نه اینکه Agent کاری را انجام دهد که برای آن طراحی نشده است. <b>جلوگیری از Context Collapse</b> 
 
یکی از مشکلات زنجیره‌های طولانی Handoff، Context Collapse است. اگر Agent اول Context را خلاصه کند، Agent دوم همان خلاصه را دوباره فشرده کند و نتیجه به Agent سوم برسد، بخشی از اطلاعات در هر انتقال از دست می‌رود. پس از چند مرحله ممکن است Agent آخر فقط نسخه‌ای ناقص از اطلاعات اولیه را در اختیار داشته باشد. [Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/aaai-apply-task-decomposition-multi-agent-azure/5-ensure-handoff-reliability-context-preservation)

برای جلوگیری از این وضعیت، Context کامل workflow باید حفظ شود و هر Agent به‌جای بازخلاصه‌سازی مداوم، Structured Output خودش را اضافه کند. در Partial Handoff نیز باید Completed Work از Remaining Work جدا باشد تا Agent بعدی بداند چه بخش‌هایی قطعی شده و چه کاری هنوز باقی مانده است. حتی با حفظ History کامل، طول زنجیره باید کنترل شود؛ افزایش Handoffها Context Token، هزینه و فشار روی Model را بیشتر می‌کند. [Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/aaai-apply-task-decomposition-multi-agent-azure/5-ensure-handoff-reliability-context-preservation)
